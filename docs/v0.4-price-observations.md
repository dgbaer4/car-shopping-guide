## Shopper workflow and boundaries

1. Open **Shopping Tracker** from the guide header, or **Add Vehicle Observation** from a recommendation. A recommendation fills in year, manufacturer, model, condition, powertrain and drivetrain where available. Exact trim and observed price come from the shopper.
2. Save locally. Each observation receives a random UUID and a UTC timestamp. One catalog configuration can have many distinct observations. Vehicle identity, condition, price observation type, price scope, provenance and verification are independent fields.
3. Use **GOOD**, **POSSIBLE** or **DON’T THINK SO**. Each group sorts by ascending price with missing prices last. The bottom control reveals rejected vehicles. Older or imported local rows can have missing prices. New entries and contributions require a positive price.
4. Edit or delete the local row, follow its permalink on the same origin and device, or export a backup. A recommendation can open the related local observations for its catalog ID. A linked observation returns to the corresponding recommendation and cost estimate when that configuration is available under the saved profile. Independent entries work without any catalog reference. A changed identity drops the original recommendation association. Listing links open in a separate tab.
5. For a voluntary contribution, review the payload, choose whether to include optional ZIP, URL path, vehicle details and nickname, and consent. Copy or download it. Hosted intake opens in a separate tab. Paste the JSON, enter the pilot invite code, give intake consent and submit. A receipt appears on the intake page after a write or a matched retry. The locally saved observation is independent of delivery, and edits and deletions apply only to the local copy.

The tracker represents user observations as unverified. Quotes and reported purchases have their own accessible text and indicators. The recommendation cards retain the original sourced ranges, attribution, date, quote overrides and ownership-cost model, with accessible published market pricing and manufacturer MSRP indicators. An observation never updates the representative price or serves as an automatic cost override. Out-the-door observations include taxes and fees and are stored separately from vehicle-only observations.

## Collection decision and data flow

| Mechanism | Fit |
| --- | --- |
| Google Forms | Simple managed form and private response sheet, native required fields and response receipt. Google Forms offers limited pre-write validation across fields and no atomic, caller-ID-based duplicate check. Prefill links would carry shopper data in the URL. Post-write cleanup would still leave malformed or duplicate rows in the response sheet. |
| Google Apps Script | The hosted page can use Google's `google.script.run` bridge for a confirmed write, shared schema validation, invitation checks and locking. A paste-based handoff keeps the static page free of cross-origin write calls and keeps contribution data and the invite code out of URLs. The owner controls deployment, access and when to open the intake. The added copy/paste step is a pilot tradeoff. |

Static guide → browser storage → consented sanitized export → Google-hosted page → validated invite, consent and payload → locked deduplication → private raw sheet → receipt. The server adds received time, a consent version and a digest of the canonical payload. An unchanged retry with the same ID receives an already-received receipt, including after a lost response. A changed payload under an already received ID returns a conflict. Keep the original contribution for retries. If a shared record needs correction, contact the owner using its ID. The pilot provides neither a public lookup endpoint nor a self-service remote update or deletion endpoint.

The intake page distinguishes pending, received, duplicate, conflict, rejected and unconfirmed delivery. Keep the same payload for an unconfirmed retry. Wait for pending submissions to finish or time out, and retry later if the service is busy. The static site's link is disabled until configured. The sanitized export supports manual owner intake in the meantime.

## Owner setup and live verification

Google account authorization, private sheet creation and Apps Script deployment remain owner tasks. Use a dedicated owner-controlled account or a restricted workspace account for the intake where available. The standalone script's spreadsheet authorization covers files accessible to that account.

1. Create a Google spreadsheet and set General access to **Restricted**. Give access only to authorized reviewers. Keep sheet sharing and web-app access separate. Record the spreadsheet ID from the URL.
2. Create a private standalone Apps Script project with the V8 runtime. Replace the default script file contents with `collection/Intake.gs`. Add an HTML file named `Intake` and paste `collection/Intake.html`.
3. Run `node tools/build_observation_intake.mjs /tmp/ObservationValidation.gs` from this branch. Add a script file named `ObservationValidation` and paste the generated contents. Regenerate when the validator changes and redeploy both script files together.
4. Generate a pilot invite code with `openssl rand -hex 24`. Compute the lowercase SHA-256 hex digest of the code with no trailing newline. For example, assign the code to a task-specific shell variable using a trusted local prompt and run `printf '%s' "$csg_invite" | openssl dgst -sha256`. In Apps Script **Project Settings → Script properties**, set `SPREADSHEET_ID` to the private sheet ID and `INVITE_SHA256` to the 64-character digest. Distribute the code directly to invited pilot shoppers. Store it outside Git and Google Sheets.
5. In the script editor, run `initializeCollection_` and grant the requested scopes. Verify all six tabs, headers and the populated dictionary. The script writes records only to `Raw_Observations`. The default blank sheet may be removed by the owner.
6. Choose **Deploy → New deployment → Web app**, with **Execute as** set to the deploying owner. Use the narrowest access policy covering pilot shoppers. For a cross-domain pilot, use the supported **Anyone with a Google account** setting where available. A Google sign-in, if required by the deployment policy, is handled by Google. The project code does not read or store the signed-in identity. If the intended audience cannot use the available settings, keep the static link disabled and use owner-mediated sanitized exports until the owner approves a suitable access policy. The app also requires the invite code for writes.
7. Before adding a public link, open the deployed `/exec` URL as a representative pilot user. Submit `tests/fixtures/observations-shared.json` with test consent and the private invite. Verify the receipt, exactly one row, a JSON cell value, and `v1` consent. Retry the same payload and check the unchanged row count. Change the price with the same ID and expect a conflict. Try the private fixture and an invalid invite and verify rejection and an unchanged sheet. Verify a pilot user cannot open the spreadsheet or read its rows, and that the app can open the hosted intake in Safari. Remove the fixture row after verification.
8. During controlled integration, set `intakeUrl` in `engine/observation-config.mjs` to the verified Google `https://script.google.com/macros/s/…/exec` deployment URL. Include the three observation modules in the integration release builder allowlist. Package and test locally, then route any staging or production promotion through CSG-I15. Keep credentials, spreadsheet ID, invite and digest out of static files, commit messages and issue or PR bodies.
9. Before inviting contributors, decide reviewer access, retention, takedown contact and publication consent. Share those terms through the pilot's owner communication. Never republish a nickname or identifying listing path by default. To close collection, remove or rotate `INVITE_SHA256` and disable or archive the web-app deployment if appropriate.

## Security and privacy assessment

- The project contains no service credentials or privileged keys. The public app hosts no write endpoint. Apps Script opens the private sheet using owner authorization. Pilot invitations gate writes independently of the web app's Google access setting, and the script checks the invite digest again inside the write lock after waiting. Owner-only setup functions are private Apps Script helpers.
- Required form controls improve entry feedback. The same validator checks lengths, control characters, UUID, date, year, enums, integer cents, mileage, ZIP and URL safety in the browser and server. Intake rejects unknown fields, including local notes and interest values. Shared listing URLs strip query and fragment. Text is rendered with text nodes. Formula-like strings can be legitimate vehicle input and remain nested in a JSON cell starting with a literal opening brace. Reviewers must write extracted text as literal data, including any later CSV import or export.
- The lock and durable UUID/digest comparison protect against overlapping retries. The private sheet retains multiple price observations for one vehicle. Different IDs for the same listing require later human or normalization review. The intake accepts one record of at most 8,000 JavaScript code units per submission, permits 50 new writes per UTC day and caps raw at 5,000 data rows. A failed write can use a daily slot. Identical retry receipts continue at capacity. The invite code is shared across this cohort and cannot attribute or fairly throttle individual users. A leak can exhaust capacity. Rotate the code or close collection if needed. Public endpoint invocation can still consume Google quotas before app controls run.
- Google can impose per-account and per-user invocation and storage limits. Apps Script currently documents a six-minute execution limit, 30 simultaneous executions per user, 1,000 simultaneous executions per script and 50,000 daily Properties reads/writes for consumer accounts versus 500,000 for Workspace accounts. Sheets documents a 10-million-cell spreadsheet limit. Limits can change and account policy can restrict deployments. This pilot uses on-demand submissions and manual review, with no scheduled execution or metered API dependency. [Apps Script quotas](https://developers.google.com/apps-script/guides/services/quotas) · [Google Sheets limits](https://support.google.com/drive/answer/37603)
- Local storage is scoped to the browser and origin and can be cleared, evicted or inaccessible. Other scripts on the same origin and people with access to the browser profile can read it. Private Markdown and JSON backups are plaintext. A nickname is self-declared. Free text and listing paths can contain identifiers despite the prompt and query removal. Owner review and minimization are required before any publication. Consent to private review does not grant public attribution. Receipt timestamps and access logging may exist on Google's infrastructure. No private notes, raw exports, or personal information belong in source control.

## Exchange format and schema

The JSON document has `format: "csg-observations"`, `version: 1` and an ordered `observations` array. An individual file contains one array item. A collection contains multiple items. Currency is USD and precision is integer cents. Date is canonical ISO 8601 UTC. UUID identifies the observation rather than the catalog vehicle. See the [JSON Schema](../data/observations.schema.json) and [test fixtures](../tests/fixtures/). Runtime also applies time-relative rules such as the current-year ceiling and a one-day future clock tolerance.

Markdown wraps the identical JSON mapping between two `---` lines. JSON mapping syntax is valid YAML 1.2 flow-style front matter. The pilot importer accepts this exact front matter representation or JSON and does not run a general YAML loader. Use private export for a lossless backup of the normalized local record, including notes and interest. Import validates the file before writing and skips existing IDs. The sanitized shared representation always excludes private notes and interest and omits optional location, link and attribution details by default. Files are versioned independently of the site label.

## Manual normalization and review contract

The future owner-triggered `workflow_dispatch` input is a **sanitized and explicitly publication-approved** JSON exchange batch from `Reviewed_Observations`, along with pinned aliases, catalog asset version and a known base commit. Keep raw submissions, rejection notes, identities, credentials and private spreadsheet exports outside GitHub. For the initial workflow, transfer the sanitized and manually reviewed batch through an owner-controlled path. Choose the transfer mechanism and credential scopes during implementation. Use the same validator plus a stricter publication allowlist.

1. Validate version and records, reject private fields and unapproved optional details, and maintain a PII review gate. Required public vehicle labels need review too.
2. Normalize makes and models with scoped, versioned aliases, then check the year, powertrain and drivetrain against the selected catalog. Record exact matches and put unmatched or ambiguous identities in a private review queue. Treat a submitted catalog reference as a hint.
3. Reject UUID conflicts. Flag semantic duplicate candidates with a conservative fingerprint using normalized vehicle descriptors, condition, type, scope, cents and suitable listing/date evidence. Keep repeated observations when the evidence supports separate observations. Preserve receipt and review history privately, and preserve public provenance, type, scope, timestamp and stable observation ID for approved records.
4. Emit a deterministic, versioned public JSON asset sorted by observation ID, a sanitized counts summary and a reviewable draft PR from an isolated import branch. Make a dry-run the default, use read permissions for validation and grant branch and draft PR write capability only to the reviewed publish step. Release promotion stays with controlled integration. There is no scheduled job or automatic catalog update.
